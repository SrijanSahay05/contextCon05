# AGENTS.md

Instructions for coding agents working in this repo. Monorepo:

- `backend/` — FastAPI (Python 3.13+), sync SQLAlchemy 2.x + psycopg 3 on Postgres, Alembic, PyMongo on MongoDB, managed with uv
- `frontend/` — Vite + React 19 + TypeScript, managed with pnpm; served by nginx in Docker
- `docs/` — architecture reference, PRDs, implementation plans, change logs

Read `docs/architecture.md` before structural work: it describes the layout, the backend layering, and how `/api` requests reach the backend.

## Commands

```bash
make install                         # uv sync (backend) + pnpm install (frontend)
make dev                             # backend + Postgres + Mongo via docker compose
make front                           # frontend dev server on :5173
make up                              # full stack in Docker (nginx on :80)
make dev-down                        # stop compose services
make db-generate MESSAGE="..."       # alembic revision --autogenerate
make db-migrate                      # alembic upgrade head
make db-push MESSAGE="..."           # generate + apply
make check                           # lint + typecheck + test, everything CI runs
make lint                            # flake8 (backend) + oxlint (frontend)
make typecheck                       # mypy --strict (backend) + tsc -b (frontend)
make test                            # pytest (needs `make dev` running) + vitest
pnpm build                           # frontend (from frontend/)
```

Always run docker compose through `make` (or pass `--env-file backend/.env`); credentials come from `backend/.env`.

## Conventions

- Read settings via `get_settings()` from `app/core/config.py`.
- New ORM models subclass `Base` and must be imported in `app/models/__init__.py`, or Alembic autogenerate will not see them.
- New routers live in `app/routes/<name>.py` as `router = APIRouter(...)` and are included in `app/main.py`. No `/api` prefix on backend routes; the proxy strips it.
- Never apply migrations unless asked. Review autogenerated revisions before applying.
- New config keys go in `Settings` and in `backend/.env.example` (with a placeholder, never a real secret).
- Never commit `.env` files.

## Docs: what to trust

- `docs/architecture.md` is current and maintained. Update it in the same change when you change the stack, the layout, or the request flow.
- `docs/implementation_plan/*` and `docs/change_logs/*` are historical records of work as it happened, not current-state specs. Trust the code over them.
- `docs/prd/*` describes intended product behaviour.

## Git workflow

- `main` is protected: no direct pushes or merges. Every change lands through a pull request with green CI (`backend` and `frontend` jobs).
- Branch from an up-to-date `main` with a prefixed name: `feat/`, `fix/`, `refactor/`, `docs/`, `chore/`, `ci/`.
- Commit messages: Conventional Commits, `type(scope): imperative summary` (≤ 72 chars), e.g. `feat(backend): add users model`. Scope is `backend`, `frontend`, `infra`, `docs`, or omitted. Body explains *why*, wrapped at 72.
- Run `make check` (needs `make dev` running for backend tests) before pushing.
- To commit and open a PR, use the `commit-and-pr` skill (`.claude/skills/commit-and-pr/SKILL.md`); other agents follow the same steps by reading it.

## Filling the PR template

`.github/pull_request_template.md` is used for every PR. Rules:

- **Title:** same format as the commit summary (`type(scope): summary`). For multi-commit PRs, summarise the whole change.
- **Summary:** 1–2 sentences on what changed and why. No file-by-file narration.
- **Changes:** bullets grouped by area (backend / frontend / infra / docs); only what a reviewer needs to know. Remove the empty `-` placeholder.
- **Type of change:** tick every box that applies; leave the rest unticked. Do not delete the list.
- **Database:** tick exactly one. If a migration is included, name the revision file.
- **How it was tested:** list the exact commands run and their outcome. Tick `make check` only if it actually passed; if something was not run, say so instead of ticking.
- **Notes for reviewers:** risks, skipped work, follow-ups. Write `None` if there are none, never leave it blank.
- Delete all HTML comments (`<!-- ... -->`) from the final body.
- Never claim a check passed that you did not run.
